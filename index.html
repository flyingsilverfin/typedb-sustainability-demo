TypeDB in five minutes

TypeDB is a database whose schema is a conceptual model. You describe your domain with entities, relations and attributes. TypeDB stores data in exactly those terms, checks every query against them, and enforces their constraints.

Three kinds of type

EntitiesThings that exist on their own: a company, a mill, a country.
RelationsConnections between things, where each participant plays a named role. An ownership has an owner and an owned. A relation can have any number of roles and can own attributes itself.
AttributesTyped values, like a name, a volume or a date, owned by entities and relations.

Types can specialise other types (sub), and an @abstract type has no instances of its own. A query for a supertype automatically finds instances of all its subtypes. That's why this model is called PERA: the polymorphic entity-relation-attribute model.

Unlike most ER implementations, nothing is translated away: relations keep their roles and identity, n-ary relations stay n-ary, and subtypes stay subtypes.

The schema is enforced

  • Queries are type-checked before they run. If no data could ever match a query (say, a country playing a role only mills can play), you get an error, not a silent empty result.
  • Writes are checked against the schema. Constraints like @key and @card are checked by the time a transaction commits, so data that breaks them never gets in.

Queries are pipelines

A TypeQL query is a sequence of clauses, each passing its results to the next: match finds data, then insert, delete, reduce (aggregate), sort or fetch act on it. Schema changes use define and undefine. The syntax guide on this page lists the main keywords.

The data

The data comes from Trase's open supply-chain data: 81 real trade flows of palm oil from East Kalimantan, Indonesia, to EU countries in 2022.

Benedict, J. J., Biddle, H., Gollnow, F., Heilmayr, R., Mueller, C., Ribeiro, V., & Suavet, C. (2024). Indonesia palm oil supply chain (2018–2022) (Version 1.2) [Data set]. Trase. https://doi.org/10.48650/X83N-7M36. Licensed CC BY 4.0.

One row is one trade flow: palm oil grown in a district (kabupaten), processed at a mill, sometimes refined, exported by one company and imported by another into an EU country. The columns fall into three groups:

  • Places: country_of_production, province_of_production, kabupaten_of_production, country_of_first_import
  • Companies and facilities: mill, refinery, exporter, importer, each with a *_group column for its parent company
  • The flow itself: product_type, volume (tonnes), fob (value in USD), palm_oil_deforestation_10_year_total_exposure (hectares)

How this excerpt was made simplifications
  • Rows: from the full dataset (~1.7M rows), only 2022 flows from East Kalimantan to the EU with all actors known, then 81 of those, chosen so that every modelling case appears. No values were invented or edited.
  • Columns: 16 of ~35 kept. Dropped: year, Trase IDs and country codes, port of export, economic bloc, sustainability scores and commitments, emissions metrics.
  • Interpretation: NOT REFINED means the flow has no refiner. When importer_group equals importer, no parent is recorded. A refinery that shares its name with an exporter is read as owned by that company.
  • Caveat: Trase flows are modelled from customs, production and facility data, not observed shipments. The insert query below rounds values (volume 3 dp, deforestation 4 dp, USD 2 dp).

Setup

You need a TypeDB server and a web browser.

  1. Set up a TypeDB server, either:
    • locally, with the installer script or Docker, or
    • as a free cloud instance: cloud.typedb.com
  2. Note the address, username and password
    • Local: http://localhost:8000, admin, password by default
    • Cloud: copy them from the cloud dashboard
  3. Connect TypeDB Studio
    • Open studio.typedb.com
    • Connect (at the top) with your credentials
    • Create a new, empty database

In Studio, paste each query into the editor and run it. Studio's default auto mode works out whether a query changes the schema or the data, and commits it for you.

Part 1 · Build the model

We read the data and model it a few columns at a time. Each step shows an ER diagram first and the TypeQL behind a reveal: try writing it yourself before you look, then run each snippet in order.

1 · Initial definitions: places

Reading the header and a first row, the easiest things to model are the places: the country, the province and the kabupaten (district) the palm oil comes from.

Places in TypeQL snippet 1
  • attribute name, value string; declares an attribute type and its value type. country_name and the other names are subtypes of name, so a query for name finds all of them.
  • entity place @abstract; is a supertype with no direct instances. sub place makes country, province and kabupaten kinds of place.
  • owns country_name @key: every country has exactly one name, and no two countries share it.

Learn more: Type hierarchies · @abstract · @key

Places contain places

Presumably the places nest: a kabupaten lies in a province, which lies in a country.

Places hierarchy in TypeQL snippet 2
  • relation containment, relates parent, relates child declares a relation and its two roles.
  • plays containment:child says which types can fill a role. A province plays both roles.
  • @card sets how many: each containment has exactly one parent and one child (@card(1)), and a place has at most one parent (@card(0..1)).
  • Running define on an existing type, like entity country here, adds to it.

Learn more: Constraining data · @card

Option 2: companies and facilities

The data sheet says each *_group column "groups the [X] column into parent companies where applicable". So there are really only companies and facilities (mills and refineries), linked by ownership, and exporter is a role a company plays, not a kind of company.

Option 2 in TypeQL snippet 3
  • A two-level hierarchy: mill and refinery are kinds of facility, and facilities and companies are kinds of legal_entity.
  • A role a supertype plays is inherited: mills and refineries can both be owned.
  • Companies are identified by their name (@key). Mills and refineries simply own a name.

4 · Trade flows

Each row of the data is one trade flow linking a district, a mill, sometimes a refinery (crude palm oil isn't refined), an exporter, an importer, a destination country and a commodity. How would you model the flow itself?

Trade flow in TypeQL snippet 6
  • One relation with seven roles. Six are required (@card(1)) and the refiner is optional (@card(0..1)).
  • The relation owns attributes of its own: volume, deforestation exposure and value. double and decimal are numeric value types.
Why not a table or a graph? what other databases do with this
  • In a relational table, the roles survive only as foreign-key column names, the optional refiner becomes a nullable column, and "exactly one mill" has to be enforced in application code or triggers.
  • In a graph database, edges connect only two nodes. Chaining edges (mill → refinery → exporter → importer) invents connections: in this dataset, following hops gives 102 mill–importer pairs, but only 63 appear in a real flow. Making each flow a node of its own keeps the facts, but nothing enforces its roles or their cardinalities, and nothing retains the semantic distinction between what is an entity node versus a relation node.

In TypeDB the seven-way relation is stored, typed and constrained as it is.

Part 2 · Load the data

With the full schema in place, one insert query loads all 81 trade flows. It creates the places, companies and facilities first, binding each to a variable such as $co_louis_dreyfus, then uses those variables to create the containment, ownership and trade-flow relations. The whole query commits as one transaction, so if anything breaks the schema, none of it is saved.

Pattern matching and polymorphism

A query lists statements that must all be true. isa facility also matches every subtype of facility. isa! matches only the exact type, so $f isa! $t binds $t to each facility's own type.

Facility ownership

A facility can sit under several layers of companies. Can one query find all of a facility's owners? A disjunction ({ … } or { … }) handles a fixed number of hops. A recursive function handles any number: with fun defines a function for this query only, and let $c in owners($f) calls it.
