1. Summary

  • Data: real Trase data. 81 rows chosen from the 2022 East Kalimantan → EU palm oil flows (CC BY 4.0), keeping only the 16 columns the schema needs.
  • Model (from the notes):
    • places;
    • company and facility (mill / refinery), linked by ownership;
    • exporter and importer as roles;
    • commodity as one type with a validated value;
    • a 6- or 7-way trade_flow relation with an optional refiner.
  • Two levels of ownership, following Joshua's reading of LDC EAST INDONESIA. A refinery that shares its name with an exporter is owned by that company, which in turn is owned by the group: refinery → LDC EAST INDONESIA → LOUIS DREYFUS. Three such chains are in the data.
  • Loading: one copy-paste insert query (241 statements). tested: commits in about 0.1 s with every cardinality check passing.
  • Queries: every headline number in §7 was checked against Python on the same CSV.

3. The data

  • Source: Trase, Indonesia palm oil v1.2.5. Citation: Benedict et al. 2024, doi:10.48650/X83N-7M36.
  • Demo selection:
    • The rows are real and unedited, drawn from the 824-row subset.
    • Mills with group UNKNOWN AFFILIATION are excluded.
    • Rows were picked with quotas per importer, about half highest-exposure and half a seeded random mix, so that every teaching case appears.
  • Columns: country_of_production, province_of_production, kabupaten_of_production, mill, mill_group, refinery, refinery_group, exporter, exporter_group, importer, importer_group, country_of_first_import, product_type, volume, fob, palm_oil_deforestation_10_year_total_exposure
  • Contents: 6 kabupaten, 41 mills, 6 refineries, 37 companies, 9 importers, 6 EU countries, 10 crude rows, and 43 of 81 flows with exposure above zero.
Say this out loud: Trase flows are modelled (SEI-PCS allocation), not observed shipments, and facility attribution comes from desk research by AidEnvironment and Auriga. The insert also rounds values (volume 3 dp, exposure 4 dp, USD 2 dp).

4. Part 1: the model (following NOTES.md)

Step 1–2 · Read a row, start with places (snippets 1 and 1.1)

Country, province and kabupaten under an abstract place, each keyed by its own *_name. Every *_name attribute (places, facilities, companies, commodities) is a subtype of one name attribute, so match $x has name $n; finds every named thing. Snippet 1.1 adds a containment relation (parent/child) so kabupaten sit in provinces and provinces in countries.

Nice live moment tested: match $x has name "LDC EAST INDONESIA"; returns two things, a refinery and a company. That's "same name, different thing" in one query.

Step 3 · Get stuck on the overlapping names, then read the dictionary (snippets 2–3)

Checked on the full subset:

  • 3 names appear as both refinery and exporter.
  • All importer names are also group names (importer_group == importer on every row).
  • FIRST RESOURCES appears in all four group columns.
exporter: Company, including subsidiaries, responsible for exporting the commodity · *_group: groups the X column into parent companies where applicable

The conclusion: there are only companies and facilities, linked by ownership, and "exporter" is a role.

The LDC reading: a company called LDC EAST INDONESIA exports and owns the refinery of the same name, and LOUIS DREYFUS is that company's parent. Snippet 3 (company plays ownership:owned) is the one-line schema change that allows this.

Evidence for the LDC reading: for all 3 refineries whose name matches an exporter, Trase's refinery_group equals that exporter's exporter_group, so the inferred chain agrees with the data. Separate facility_name and company_name attributes make "same name, different thing" visible in the schema.

Step 4 · Commodities (snippet 4)

Option (a): one entity type, with commodity_name @values("PALM OIL", "REFINED PALM OIL") and @key.

  • Note that @key plus @values already limits the type to at most two instances, which is a neat point.
  • The model-(c) challenge answer (04c) puts @key @values("…") on each subtype's owns. tested: a second palm_oil fails with a key violation, and a palm_oil named "REFINED PALM OIL" fails with a @values violation (CNT8).

Step 5 · The trade flow (snippet 5)

A 6-way relation, or 7-way when a refiner is present, with refiner @card(0..1). Port and year are dropped on purpose; say so on stage.

5. Full schema (schema/full-schema.tql) tested

Generated by scripts/build.py from the snippets in tutorial order: 1, 1.1, 2, 3, 4, 5. Validated on TypeDB CE 3.13.6, both in one go and snippet by snippet. Fixes the snippets need compared with NOTES.md:

  • entity commidity → commodity (snippet 4).
  • Added entity commodity, plays trade_flow:commodity; (missing from snippet 5).
  • Snippet 1.1: contains:child → containment:child. The @card(0..1) goes on the child roles ("at most one parent"). On province plays containment:parent it would allow only one kabupaten per province, and the data has six.
define

attribute name, value string;

### Places ###

attribute country_name, sub name;
attribute province_name, sub name;
attribute kabupaten_name, sub name;

entity place @abstract;

entity country,
  sub place,
  owns country_name @key;

entity province,
  sub place,
  owns province_name @key;

entity kabupaten,
  sub place,
  owns kabupaten_name @key;

### Places hierarchy ###

relation containment,
  relates parent @card(1),
  relates child @card(1);

entity country, plays containment:parent;
entity province,
  plays containment:child @card(0..1),   # at most 1 parent
  plays containment:parent;
entity kabupaten,
  plays containment:child @card(0..1);   # at most 1 parent

### Companies and facilities ###

attribute facility_name, sub name;
attribute company_name, sub name;

entity facility @abstract,
  owns facility_name,
  plays ownership:owned @card(0..1);   # at most 1 owner
entity mill,
  sub facility;
entity refinery,
  sub facility;

entity company,
  owns company_name @key,
  plays ownership:owner;

relation ownership,
  relates owner @card(1),
  relates owned @card(1);

# companies can also be owned (by a parent company)
entity company,
  plays ownership:owned @card(0..1);

### Commodities ###

attribute commodity_name,
  sub name,
  value string @values("PALM OIL", "REFINED PALM OIL");  # validated enum

entity commodity,
  owns commodity_name @key;

### Trade flow ###

attribute volume_tonnes, value double;
attribute deforestation_ha, value double;
attribute usd, value decimal;

relation trade_flow,
  relates origin @card(1),
  relates mill @card(1),
  relates refiner @card(0..1),   # optional!
  relates exporter @card(1),
  relates importer @card(1),
  relates destination @card(1),
  relates commodity @card(1),
  owns volume_tonnes @card(1),
  owns deforestation_ha @card(1),
  owns usd @card(1);

entity kabupaten, plays trade_flow:origin;
entity mill, plays trade_flow:mill;
entity refinery, plays trade_flow:refiner;
entity company,
  plays trade_flow:importer,
  plays trade_flow:exporter;
entity country,
  plays trade_flow:destination;
entity commodity,
  plays trade_flow:commodity;
Design note to mention (or not): company and facility share no supertype. That's fine for the model, but any "who controls this party?" function needs one version for companies and one for facilities (see Q7). A shared abstract party supertype would allow a single function. It's a nice "the model shapes the queries" aside.

Q6 · The connection trap: n-ary vs. binary hops

# true mill→importer pairs
match trade_flow (mill: $m, importer: $i);
select $m, $i; distinct;
reduce $real_pairs = count;               # 69

# if the model only kept binary hops (refined chain)
match trade_flow (mill: $m, refiner: $r);
select $m, $r; distinct;
match trade_flow (refiner: $r, exporter: $e);
select $m, $e; distinct;
match trade_flow (exporter: $e, importer: $i);
select $m, $i; distinct;
reduce $hop_pairs = count;                # 102

102 pairs from hops (refined chain only) against 63 real pairs that go through a refinery, so 39 never happened. The 69 real pairs in total also include 6 crude-only pairs, so compare 102 with 63, not with 69. Counting crude mill→exporter hops as well gives 108 = 69 real + the same 39 spurious, none missing, which matches Python. See Q6b for what these numbers mean. That variant needs an or, so wrap it in a function to avoid the bug in §10:

with fun hop_exporters($m: mill) -> { company }:
  match
    { trade_flow (mill: $m, refiner: $r); trade_flow (refiner: $r, exporter: $e); } or
    { $f isa trade_flow, links (mill: $m, exporter: $e); not { $f links (refiner: $x); }; };
  return { $e };
match $m isa mill; let $e in hop_exporters($m);
match trade_flow (exporter: $e, importer: $i);
select $m, $i; distinct;
reduce $hop_pairs_incl_crude = count;     # 108

This is the core argument against binary decomposition, shown with real data. Also worth noting: 16 mills supply more than one importer.

Q6b · Reification vs. binary edges: what the counts mean

Short version: a reified trade flow is essentially the same as our trade_flow relation, and it gets the right answer. The wrong counts come from a different option: modelling the supply chain as binary edges with no flow node at all.

Three ways to store one Trase row outside TypeDB

RepresentationWhat one row becomesMill→importer pairsCorrect?
TypeDB trade_flow relationOne relation with 6–7 role players69✓
Reified flow: a property-graph node, or a SQL tableA TradeFlow node with labelled edges to each participant, or a row with 7 foreign keys69✓ same information
Binary edges (refined chain)Edges mill→refinery, refinery→exporter, exporter→importer; the flow itself is gone102 = 63 real + 39 that never happened✗
Binary edges, including crude mill→exporter edgesAs above, plus direct mill→exporter edges for crude oil108 = 69 real + the same 39✗

A. Reification: the relation, built by hand

// property graph (Cypher-style): one node per flow, one edge per role
(f:TradeFlow)-[:MILL]->(m:Mill)
(f)-[:REFINER]->(r:Refinery)
(f)-[:EXPORTER]->(e:Company)
(f)-[:IMPORTER]->(i:Company)
(f)-[:DESTINATION]->(c:Country) ...

MATCH (m:Mill)<-[:MILL]-(f:TradeFlow)-[:IMPORTER]->(i:Company)
RETURN count(DISTINCT [m, i])            // 69, the same as TypeDB

Because every participant hangs off the same flow node, the fact "this mill's oil went to this importer" is never broken apart. So yes: reification gives you the relation. The difference is in what the database knows about it, not in the answers:

  • No declared roles: :MILL is just an edge label. Nothing says only mills may sit at the end of a :MILL edge, or that a TradeFlow node must have one.
  • No cardinality: nothing enforces exactly one mill and at most one refiner per flow. A flow node with two :MILL edges or none is accepted without complaint. TypeDB rejects those at commit (Q9).
  • The relation is just a node: the database can't tell a reified relationship from an ordinary entity. Every query has to navigate through it explicitly, and tools can't treat it as a relationship.
  • SQL is the same story: a trade_flow table with 7 foreign keys preserves the fact, but roles are only column names, and "optional refiner" is just a nullable column.

B. Binary edges: where the connection trap comes from

// the "supply-chain graph" many people draw first
(:Mill)-[:SUPPLIES]->(:Refinery)-[:SUPPLIES]->(:Company exporter)-[:SELLS_TO]->(:Company importer)

MATCH (m:Mill)-[:SUPPLIES]->(:Refinery)-[:SUPPLIES]->(:Company)-[:SELLS_TO]->(i:Company)
RETURN count(DISTINCT [m, i])            // 102, but only 63 of these are real

Each edge is true on its own, but the edges no longer remember which flow they came from. Following a path through them joins hops from different flows.

A real example from the demo data
  • The mill ANUGERAH AGUNG PRIMA ABADI sends oil to KUTAI REFINERY NUSANTARA (true).
  • KUTAI REFINERY NUSANTARA exports, and sells to APICAL MIDDLE EAST FZCO (true), but that oil comes from other mills: AGRI EASTBORNEO KENCANA, BIMA AGRI SAWIT (POM 10), DWIWIRA LESTARI JAYA, HAMPARAN PERKASA MANDIRI, ….
  • So the path ANUGERAH → KUTAI → APICAL exists in the binary graph, even though in the data this mill's oil only ever went to AAA OILS & FATS.
For a deforestation-traceability question, that's a false accusation: APICAL would be linked to a mill it never sourced from.

How the TypeQL in Q6 simulates this: the three-stage pipeline keeps only $m, $e between stages (select … ; distinct;). That deliberately throws away which flow linked them, which is exactly what binary edges lose. The one-pattern query trade_flow (mill: $m, importer: $i) keeps it.

What to say on stage: "Binary edges get traceability wrong: 39 links in this small sample that never happened. The standard fix is reification, a node or table per flow, and that fix is a relation, built by hand. TypeDB makes it the primitive, with declared roles, cardinalities and types that are checked on every write. In graph and relational stores it stays a convention."

Q7 · Two-level ownership: refinery → operator → group

match
  ownership (owned: $r, owner: $c); $r isa refinery;
  ownership (owned: $c, owner: $g);
  $r has facility_name $refinery; $c has company_name $operator; $g has company_name $group;
select $refinery, $operator, $group;

Result: LDC EAST INDONESIA → LDC EAST INDONESIA → LOUIS DREYFUS · ADHITYA SERAYAKORITA → … → FIRST RESOURCES · KUTAI REFINERY NUSANTARA → … → ROYAL GOLDEN EAGLE.

Recursive version, owners at any depth untested on this schema. The same pattern was tested on an earlier schema. There's no shared supertype, so it needs one function per kind:

fun company_owners($c: company) -> { company }:
  match
    { ownership (owned: $c, owner: $p); } or
    { let $q in company_owners($c); ownership (owned: $q, owner: $p); };
  return { $p };
fun facility_owners($f: facility) -> { company }:
  match
    { ownership (owned: $f, owner: $p); } or
    { ownership (owned: $f, owner: $o); let $p in company_owners($o); };
  return { $p };

Q8 · Roles, not subtypes: companies controlling several roles

with fun controllers($x: company) -> { company }:
  match
    { $c is $x; } or
    { ownership (owned: $x, owner: $c); } or
    { ownership (owned: $x, owner: $p); ownership (owned: $p, owner: $c); };
  return { $c };
with fun facility_controllers($x: facility) -> { company }:
  match
    { ownership (owned: $x, owner: $c); } or
    { ownership (owned: $x, owner: $p); let $c in controllers($p); };
  return { $c };
match
  $f isa trade_flow, links ($role: $x);
  { $x isa company; let $c in controllers($x); } or
  { $x isa facility; let $c in facility_controllers($x); };
  $c has company_name $company;
select $company, $role; distinct;
reduce $roles = count groupby $company;
match $roles > 1;
sort $roles desc;

Result: FIRST RESOURCES 4 · SINAR MAS 3 · WILMAR 3 · LOUIS DREYFUS 3 · ROYAL GOLDEN EAGLE 2 · and the three operator companies (LDC EAST INDONESIA, ADHITYA SERAYAKORITA, KUTAI REFINERY NUSANTARA) with 2 each, as refiner (through the refinery they own) and as exporter.

Talking points:

  • Variables range over role types ($role).
  • Query-level with fun functions need no schema change.
  • This is the data's own proof that "exporter" can't be a subtype.
  • It uses or and distinct but feeds into reduce, and its results matched Python. Still, rehearse it.

10. TypeDB issues found while testing

Likely bug: distinct after an inline or streams duplicate rows (local dev-mode server, Python driver 3.12.3). The duplicates have identical IIDs. 
match { $f isa trade-flow, links (mill: $m, exporter: $e); }
  or { $g isa trade-flow, links (mill: $m, exporter: $e); };
select $m, $e; distinct;     # 334 rows, only 205 unique (earlier schema)
  • Adding reduce count gives the correct total, but a further match stage or a sum propagates the duplicates. This gave 413 instead of 348, and exactly doubled one company's exposure.
  • An 80-row case deduplicated correctly. Whether size or batching matters is unverified.
  • Workaround: put the or inside a function.
Also seen:
  • REP44 when the same negation-local variable name is used in both or branches.
  • INF7 when sorting by an entity variable, probably by design.
  • A generic INF11 error when inserting an abstract type. A clearer message would help teaching.
