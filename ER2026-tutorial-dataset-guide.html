ER 2026 Tutorial Dataset

Building Executable ER Models · Wed 7 Oct · dataset choice, the modelling walkthrough, a tested schema, and an incremental teaching plan. Revised 5 Oct 2026, with the ownership model taken from the Trase data dictionary.

Legend. tested means the item was run against the local TypeDB 3.x server on the real subset; its numbers were also checked independently in Python where noted. untested means it was written to the 3.x grammar but not executed.

1. Summary

Use Trase's Indonesia palm oil supply-chain data (v1.2.5, CC BY 4.0), cut down to 2022 flows from East Kalimantan to EU countries: 824 rows. Each row is a genuine n-ary fact:

kabupaten (district) → mill → [refinery] → exporter → port → importer → EU country · commodity · volume · FOB value · 10-yr deforestation exposure
  • N-ary: 8 role players per flow. Splitting a flow into binary hops gives 348 mill→importer pairs where only 313 are real. That's the connection trap, shown on real data. tested
  • Subtyping: party → company / facility → mill / refinery / port; place → country / province / kabupaten; commodity → crude / refined.
  • One kind of company, linked by recursive ownership. The CSV seems to have four "group" columns. The data dictionary shows they all name a parent company, so there's one company type plus an ownership relation. This is the tutorial's best modelling moment (§4).
  • Roles, not subtypes: FIRST RESOURCES controls parties in 4 different roles (mill, refinery, exporter, importer), so "exporter" can't be a subtype. tested
  • Executable: the schema rejects a typed-wrong role player and a duplicate key at compile or write time, and missing data or a second parent at commit. tested
  • Headline numbers: 193.7 kt, 9,368 ha of 10-year deforestation exposure, and 59% of flows have exposure above zero. Loads in 0.7 s.

4. From CSV to model: the modelling walkthrough

This is the process Joshua followed. It works well on stage, because the audience goes through the same realisations.

Step 1 · Read the header and one row, and start writing types down

The first instinct is one entity type per column: Mill, MillGroup, Refinery, RefineryGroup, Exporter, ExporterGroup, Port, Importer, ImporterGroup, Country.

Step 2 · Get stuck: the same names appear in different columns

# mill                         mill_group              refinery
AGRI EASTBORNEO KENCANA         KENCANA AGRI            NOT REFINED
NIAGA MAS GEMILANG              JC CHEMICAL             LDC EAST INDONESIA
TAPIAN NADENGGAN (JAK LUAY)     SINAR MAS               SMART TBK (SURABAYA REFINERY)
# refinery_group   exporter                                  exporter_group
NOT REFINED        SUMBER HIJAU UTAMA                        ROYAL GOLDEN EAGLE
LOUIS DREYFUS      LDC EAST INDONESIA                        LOUIS DREYFUS
SINAR MAS          SINAR MAS AGRO RESOURCES AND TECHNOLOGY   SINAR MAS

Measured on the subset:

  • Refinery and exporter: 3 names appear as both (LDC EAST INDONESIA, KUTAI REFINERY NUSANTARA, ADHITYA SERAYAKORITA). In 588 of the 824 rows the refinery name equals the exporter name.
  • Groups and importers: all 10 importer names also appear as group names.
  • One group, four columns: FIRST RESOURCES appears in all four group columns.

The question is whether a matching name means the same thing. Not necessarily: a refinery is a plant, and an exporter is a legal entity.

Step 3 · Read the data dictionary

exporter: Company, including subsidiaries, responsible for exporting the commodity
exporter_group: Corporate group responsible for exporting the commodity (groups the exporter column into parent companies where applicable)
mill_group: Corporate group which the mill belongs to …
refinery: … Facilities data obtained from AidEnvironment and Auriga's desk-based research

What can be inferred from it, checked against the data:

  1. A "group" is a parent company. So there's one company type, and "group" is a role in ownership(parent, subsidiary). Ownership is recursive. Each mill, refinery and exporter has exactly one group (checked), so subsidiary is at most one.
  2. "Where applicable" means the group falls back to the company's own name. importer == importer_group in all 824 rows, so no parent was assigned to any importer. The loader must not create self-ownership; ORM would call that an irreflexive ring constraint.
  3. Exporter and importer are roles played by companies, and they mean responsible for the trade. "Including subsidiaries" means each value is already a company aggregate.
  4. Facilities link straight to a parent; no operating company is given. Linking a refinery to its same-named exporter would be inferred from names, so leave it out or label it as inferred.
  5. Facility data comes from research, not declarations, which is a provenance hook (see §9).
  6. Mill group UNKNOWN AFFILIATION is a placeholder value (5 mills). Treat it as having no parent.

Step 4 · The resulting model

CandidateVerdict

5. Schema tested

define
  attribute name, value string;
  attribute trase-id, value string;
  attribute year, value integer;
  attribute volume-t, value double;
  attribute fob-usd, value double;
  attribute deforestation-ha, value double;

  # places: nested geography
  entity place @abstract,
    owns name @card(1), owns trase-id @key,
    plays containment:container, plays containment:contained;
  entity country sub place, plays trade-flow:destination;
  entity province sub place;
  entity kabupaten sub place, plays trade-flow:origin;
  relation containment, relates container @card(1), relates contained @card(1);

  # parties: companies and facilities, linked by (recursive) ownership
  entity party @abstract,
    owns name @card(1),
    plays ownership:subsidiary @card(0..1);        # at most one parent
  entity company sub party,
    plays ownership:parent,
    plays trade-flow:exporter,                         # roles, not subtypes
    plays trade-flow:importer;
  entity facility @abstract, sub party;
  entity mill sub facility, owns trase-id @key, plays trade-flow:mill;
  entity refinery sub facility, owns trase-id @key, plays trade-flow:refinery;
  entity port sub facility, plays trade-flow:port;
  relation ownership, relates parent @card(1), relates subsidiary @card(1);

  # commodities
  entity commodity @abstract, owns name @card(1), plays trade-flow:commodity;
  entity crude-palm-oil sub commodity;
  entity refined-palm-oil sub commodity;

  # the n-ary fact: one Trase row
  relation trade-flow,
    relates origin @card(1),
    relates mill @card(1),
    relates refinery @card(0..1),                # crude oil skips the refinery
    relates exporter @card(1),
    relates port @card(1),
    relates importer @card(1),
    relates destination @card(1),
    relates commodity @card(1),
    owns year @card(1), owns volume-t @card(1),
    owns fob-usd @card(1), owns deforestation-ha @card(1);

  # derived: every owner above a party, at any depth
  fun owners($x: party) -> { company }:
    match
      { ownership (subsidiary: $x, parent: $p); } or
      { let $q in owners($x); ownership (subsidiary: $q, parent: $p); };
    return { $p };

  # derived: the party itself if it is a company, plus all its owners
  fun controllers($x: party) -> { company }:
    match
      { $c isa company; $c is $x; } or
      { let $c in owners($x); };
    return { $c };

Design choices to explain

  • Why @card(1) on every relates: in 3.x a role defaults to @card(0..1), so a role can be left empty. Making each role mandatory gives Chen-style total participation.
  • Why plays ownership:subsidiary @card(0..1): the data dictionary implies one parent per party, and the data confirms it. A second parent is rejected at commit (Q7).
  • Why party: companies and facilities share an abstract supertype, so ownership and the owners/controllers functions apply to both. Single inheritance is enough here.
  • Why functions: "controls" and "owns at any depth" are derived facts, so they're defined once and reused. Wrapping the disjunction in controllers() also avoids a duplicate-rows issue (§10).
  • Ports are keyed by name: Trase gives ports no ID. This is an honest wart, and you can mention it.

6. Loading

  • A Python script generates a static data.tql of 1,075 single-line statements, in four passes. tested
    1. 51 companies, by name (exporters, importers and every group value).
    2. Places and facilities.
    3. 92 ownership links. Self-groups and placeholder values are skipped.
    4. 824 flows, each a match … insert … that looks up its eight role players.
  • Load time: 0.7 s on a local server, in one write transaction, with all cardinality checks passing at commit. The browser environment is untested.
  • Placeholder values:
    • NOT REFINED: insert the flow with no refinery role player.
    • importer_group == importer: no ownership link.
    • UNKNOWN AFFILIATION: currently loaded as a company. It should be skipped, or ownership left absent (5 mills); see to-dos.
  • Files: the v2 schema, data and loader are in the session scratchpad (palm2/). The schema.tql/data.tql in this folder are the older v1 model, with a separate group type. Copy v2 over before Wednesday.

7. Queries

Q1 · Polymorphism: every facility, by kind tested

match $f isa facility; $f isa! $t;
reduce $n = count groupby $t;

Result: mill 80 · refinery 6 · port 4. One query over the supertype returns every subtype.

Q2 · Reading an n-ary fact: where does one mill's oil go? tested

match $m isa mill, has name "YUDHA WAHANA ABADI";
  trade-flow (mill: $m, importer: $i, destination: $c);
  $i has name $in; $c has name $cn;
select $in, $cn; distinct;

Result: 15 importer–country pairs. A query names only the roles it cares about and leaves the other five unmentioned.

Q3 · The tier-3 challenge: deforestation exposure by EU importer tested

match
  $f isa trade-flow, links (importer: $i, mill: $m), has deforestation-ha $d;
  $d > 0.0; $i has name $importer;
reduce $total-ha = sum($d) groupby $importer;
sort $total-ha desc;

Result: LOUIS DREYFUS 6,047 ha · FIRST RESOURCES 2,016 · GOLDEN AGRI INTERNATIONAL 804 · APICAL MIDDLE EAST 221 · AAA OILS & FATS 117 · …

Q4 · Roles, not subtypes: companies controlling several roles tested

match
  $f isa trade-flow, links ($role: $x);
  let $c in controllers($x);
  $c has name $company;
select $company, $role; distinct;
reduce $roles = count groupby $company;
match $roles > 1;
sort $roles desc;

Result: FIRST RESOURCES 4 · SINAR MAS 3 · WILMAR 3 · LOUIS DREYFUS 3 · ROYAL GOLDEN EAGLE 2. Two features a CM audience will notice: variables range over role types ($role), and the recursive function walks the ownership hierarchy.

Q5 · The connection trap: n-ary vs. binary hops tested (checked in Python)

# true mill→importer pairs, read straight off the n-ary facts
match trade-flow (mill: $m, importer: $i);
select $m, $i; distinct;
reduce $real-pairs = count;          # 313

# the same question if the model only kept binary hops: chain them stage by stage
match trade-flow (mill: $m, refinery: $r);
select $m, $r; distinct;
match trade-flow (refinery: $r, exporter: $e);
select $m, $e; distinct;
match trade-flow (exporter: $e, importer: $i);
select $m, $i; distinct;
reduce $hop-pairs = count;           # 348

35 spurious mill→importer links, none missing. Crude flows add no new pairs, so the refined-only chain gives the full answer. It also shows multi-stage pipelines: each stage keeps only the variables the next hop needs.

Q6 · Recursion: exposure by controlling company, at any ownership depth tested (checked in Python)

match
  $f isa trade-flow, links ($role: $x), has deforestation-ha $d;
  $d > 0.0;
  let $c in controllers($x);
  $c has name $company;
select $company, $f, $d; distinct;       # count each flow once per company
reduce $ha = sum($d), $flows = count groupby $company;
sort $ha desc;

Result: LOUIS DREYFUS 6,047 ha / 60 flows (the same as its subsidiary LDC EAST INDONESIA) · KUALA LUMPUR KEPONG 3,202 / 58 · TRIPUTRA AGRO PERSADA 2,637 / 110 · FIRST RESOURCES 2,016 / 7 · …

Teaching point: this is the recursion that matters. In Trase the full supply chain sits in each n-ary row, so the tier-3 question (Q3) needs no recursion at all. The recursive part is the ownership question: "which parent companies are exposed, through any subsidiary or facility, in any role?" The select … distinct before reduce stops a flow being counted twice when a company controls two of its roles. That's a good discussion of bag versus set semantics.

Q8 · Integrity check the schema can't declare: no self-ownership tested

match ownership (parent: $x, subsidiary: $x);
reduce $self-owned = count;               # 0

ORM would declare this as an irreflexive ring constraint. In TypeDB it's a check query. Mention it when you refer back to Halpin.

8. Teaching plan (90 min), aligned with the published outline

1.1 · Introduction, ER as the source (10 min)

Chen's ER diagram of the chain on one slide, with one big diamond, Trade Flow, and its 8 edges. Pose the question: "Which EU importers, and which parent companies, carry deforestation risk from mills three tiers upstream?" Cite Chen 1976, Taxis/Galileo, and the Embley–Liddle–Pastor manifesto by name. Liddle and Pastor are in the room.

1.2 · What translations lose (10 min)

  • Relational: the diamond becomes a table of 8 foreign keys. Roles become column names, subtypes become nullable columns or extra tables, and participation constraints move into triggers.
  • Property graph: the diamond has to be reified as a node, or split into binary edges, which creates spurious paths (preview Q5). Acknowledge Link & Skavantzos's ER-on-property-graph work from ER 2025, and say what it still lacks.
  • ORM nod: refer back to Halpin's keynote the day before. Objectification ≈ a relation that plays roles. Irreflexive ring constraint = Q8.

1.3 · PERA and the ER→TypeQL mapping (10 min)

Show a mapping table: entity → entity; relationship → relation; role → relates/plays; attribute → attribute + owns; ISA → sub; participation → @card; key → @key; derived relationship → fun. Departures: attributes are first-class values; single inheritance only; relations own and play; and a role defaults to @card(0..1).

2.1 · Setup + modelling from the CSV (10 min) · the key segment

Run §4 live:

  1. Header plus one row: ask the room "what are the entities?"
  2. Show the overlapping names.
  3. Read the data dictionary aloud.
  4. Arrive at company + ownership + roles.

Let the audience suggest exporter-as-subtype, then disprove it with the FIRST RESOURCES fact. This is ER modelling done on real data, and it's what this audience values.

2.2 · Schema, incrementally (10 min)

  1. Places: place @abstract, subtypes, containment.
  2. Parties: party → company / facility → mill / refinery / port, plus ownership.
  3. trade-flow with 8 roles. Pause on refinery @card(0..1) (crude oil).
  4. Commodities as subtypes.

Each step is a separate define.

2.3 · Load data, first queries (10 min)

Load data.tql, then run Q1 and Q2. Challenge: "Which ports does oil for LOUIS DREYFUS leave from?"

2.4 · Polymorphic and recursive queries (15 min)

Q3 (the tier-3 challenge from the proposal), then Q5 (the connection trap), then define owners/controllers and run Q4 and Q6 (recursion over ownership). Challenge: "Which parent company is exposed through the most flows?" (TRIPUTRA AGRO PERSADA, 110)

2.5 · Extend the model live and introspect it (10 min)

Add eudr-risk to country (§9), run Q7 (rejected writes) and Q8, then query the schema: match $t sub party; · match trade-flow relates $r;.

3 · Wrap-up (5 min; take 10 if possible)

Positioning against relational, property-graph and OWL approaches. Open problems: dynamics (de Brock), multi-level types, and constraints that need queries (ring, set-comparison). Final slide: repo link, a QR code, and "bring me your model".

9. Extensions

EUDR country risk untested

define
  attribute eudr-risk, value string @values("low", "standard", "high");
  entity country, owns eudr-risk @card(0..1);

Indonesia is standard; EU members are low (Reg. (EU) 2025/1093, checked against a secondary source only). This works well as the live-extension step.

Provenance untested

Facility attribution comes from desk research, and flows are modelled. Add relation attribution, relates attributed, relates source with trade-flow plays attribution:attributed. That's a relation playing a role in another relation, which is a natural PERA showcase and appeals to the provenance researchers attending (Ram, Rowland, Kiamanesh).

Facility operator (inferred)

relation operation, relates operator, relates facility, filled where a refinery name equals an exporter name (3 refineries, 588 rows). Label it as inferred from matching names. It's a good lead-in to the "name ≠ identity" discussion.

RSPO certification (Universal Mill List)

The UML shares no ID with Trase, and a naive name match covered only 25 of 80 mills. Curate by hand or skip.

Consumer products (optional, partly curated)

Open Food Facts gives real product → ingredient trees. The product → importer links would have to be invented and labelled illustrative. Without this layer the data is 100% real.

10. TypeDB issues found while testing

Likely bug: distinct after or streams duplicate rows. Seen on the local server (development mode, Python driver 3.12.3). The duplicate rows have identical IIDs. 
match { $f isa trade-flow, links (mill: $m, exporter: $e); }
  or { $g isa trade-flow, links (mill: $m, exporter: $e); };
select $m, $e; distinct;            # 334 rows, only 205 unique
# + "reduce $n = count;"                → 205 (correct)
# + a further match stage, or reduce sum → duplicates propagate

It showed up twice:

  • A hop-join returned 413 instead of 348.
  • An inline-disjunction version of Q6 exactly doubled LOUIS DREYFUS (12,094 ha / 120 flows instead of 6,047 / 60).

A small case ({ $m isa mill; } or { $m isa mill; }, 80 rows) dedupes correctly, so it may depend on result size or batching. That's a hypothesis, not verified. Workaround used in this guide: put the disjunction inside a function (controllers()). The results then match Python exactly.

Also seen:
  • Using the same negation-local variable name (e.g. not { $f links (refinery: $x); }) in both branches of an or fails with REP44 ("variable 'x' must be bound").
  • sort $m on an entity variable fails with INF7, which is probably by design.
  • Inserting an abstract type fails with a generic type-inference error (INF11) rather than an "abstract type" message, which is worth improving for teaching.
